# Concrete source dependency and provider contracts

**Mandatory direct EDP-Serial 0.1.0**, which recursively depends on **EDP-System 0.1.0**. EDP-System `Framework::Provider<Serial::Domain, Offers<Offer<ByteStreamWriter>>>` is the only abstract Composition contract imported. **Mandatory native ESP-IDF** UART driver header/ABI `<driver/uart.h>` and `esp_driver_uart` component is supplied by the selected board SDK; no EDP-Platform-ESP-IDF requirement is falsely added to this provider.

The actual provider Type `Serial::ESP_IDF::UartFifoByteStreamWriter` is the concrete offered `ByteWriteEndpoint` under exact C++20 `TryWrite(span<const byte>) noexcept` and `ByteWriteResult`. Its only state is an explicitly selected `uart_port_t`. The SDK owns FIFO and actual `uart_driver_install`, which must have tx_buffer_size=0; wrong driver profile is invalid even if the C++ endpoint Type compiles.

**Optional application graph:** EDP-Serial's `EdlgFramePump` imports EDP-Logging; `BoundedEdlgFrameQueue` also imports EDP-Threading. These are *not* automatically required by this concrete, and neither abstract library may acquire a reverse dependency on EDP-Serial-ESP-IDF. CMake declares `REQUIRES esp_driver_uart edp_serial`, where the app supplies the `edp_serial` Component. The PIO manifest exposes the IDF-backed Arduino-ESP32 and ESP-IDF targets **only when** actual toolchain support for `driver/uart.h` and native ABI has been verified.
